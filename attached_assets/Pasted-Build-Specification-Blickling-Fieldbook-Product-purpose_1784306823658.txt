Build Specification: Blickling Fieldbook

Product purpose

Build a mobile-first progressive web application called Blickling Fieldbook.

The app will allow countryside staff to record issues, observations and completed work while moving around a large rural estate.

A user must be able to:

1. Record their current location.
2. Add a short title and description.
3. Select an observation category.
4. Add photographs.
5. set a priority.
6. Decide whether follow-up action is required.
7. Assign the resulting action to a team member.
8. Track the action through to completion.
9. View observations and actions on a map.
10. Generate a simple management summary.

The application should initially be suitable for one property and a small team, but the architecture should allow additional properties and teams to be added later.

---

1. Preferred technical approach

Create the application as a responsive full-stack web app that works well on Android and iPhone browsers.

Use:

- TypeScript throughout.
- React for the user interface.
- A modern full-stack React framework supported by the Replit environment.
- PostgreSQL for persistent data.
- An ORM such as Drizzle or Prisma.
- Leaflet with OpenStreetMap tiles for the interactive map.
- A PWA service worker so the app can be installed on a phone.
- IndexedDB for temporarily storing unsent field records when there is no connection.
- Server-side authentication.
- Secure object storage for uploaded images.
- Zod or an equivalent library for validation.
- A simple automated test suite for critical workflows.

Use environment variables for all secrets and service credentials.

Do not hard-code API keys, passwords or sensitive configuration.

---

2. Design principles

The application will normally be used outdoors, sometimes in poor weather and with weak mobile reception.

The interface must therefore be:

- Mobile-first.
- Fast to open.
- Usable with one hand.
- Clear in bright daylight.
- Based on large buttons and generous touch targets.
- Minimal in the number of required fields.
- Capable of saving a draft offline.
- Easy to use without specialist training.

Avoid dense dashboards, small icons, complicated menus and excessive text.

Use plain English throughout.

4. Core terminology

Use the following terms consistently.

Observation

Something noticed or recorded in the field.

Examples:

- A fallen tree across a path.
- Excessive deer browsing.
- A damaged gate.
- A veteran tree feature.
- A patch of invasive plants.
- A machinery defect.
- A completed habitat-management task.

Action

A task created because an observation requires follow-up.

Examples:

- Remove fallen limb.
- Inspect tree within seven days.
- Repair field gate.
- Recut path edge.
- Survey invasive species extent.

An observation may have no action, one action or several actions.

6. Priority levels

Use four priorities:

Low

No immediate action required.

Normal

Include in routine work planning.

High

Requires prompt attention.

Urgent

Potential immediate risk to people, property, operations or the environment.

Show urgent and high-priority records prominently, but do not rely on colour alone. Include a written priority label and an icon.

9. Observation creation workflow

Create a prominent button labelled:

Record an observation

The mobile workflow should use a short step-by-step form.

Step 1: Location

Attempt to capture the phone's GPS location.

Show:

- Latitude.
- Longitude.
- Estimated GPS accuracy.
- A small map preview.
- A button to retry GPS.
- An option to manually move the map pin.
- An option to continue without GPS if necessary.

Store the GPS accuracy value.

Allow the user to select a saved estate area or named location.

Examples of named locations to include as sample data:

- Hercules Wood
- Great Wood
- Tollands Meadow
- Abel Heath
- Leaselands
- Holly's Grove
- The Beeches
- Mount Covert
- Osier Carr
- Parkland
- Gardens
- Moorgate

Step 2: Category and title

Required fields:

- Category.
- Short title.

The title should be limited to approximately 100 characters.

Example:

“Fallen oak limb obstructing footpath”

Step 3: Details

Fields:

- Description.
- Priority.
- Date and time observed.
- Is follow-up action required?
- Is this a potential safety issue?
- Is public access affected?
- Is machinery or specialist equipment likely to be required?

Allow voice dictation through the browser where supported, with typing available as the fallback.

Step 4: Photographs

Allow the user to:

- Take a photograph using the phone camera.
- Select an existing photograph.
- Upload several photographs.
- Remove an image before submission.
- Add a caption to each image.

Compress large images before upload while retaining enough resolution for inspection and evidence.

Where available, record:

- Image upload date.
- Uploading user.
- Image orientation.
- Whether the image was taken during observation creation or added later.

Do not make photographs mandatory.

Step 5: Review and submit

Show a clear summary.

The user can:

- Submit the observation.
- Save as a draft.
- Create an action immediately.
- Cancel and discard the record.

When offline, save the complete observation locally and clearly label it:

Waiting to sync

Automatically attempt to sync when connectivity returns.

Never silently discard an unsynced observation.

19. Offline behaviour

Offline support is important but must be implemented conservatively.

For the first version:

- Allow new observations to be completed offline.
- Store offline observations and image references in IndexedDB.
- Show a visible count of records waiting to sync.
- Sync automatically when the connection returns.
- Provide a manual retry button.
- Prevent duplicate submissions by giving every offline record a locally generated unique ID.
- Show whether the latest sync succeeded or failed.
- Retain failed records until the user explicitly deletes them.

Do not initially allow complex offline editing of existing records.

That can be added later.

---

20. Authentication and security

Implement secure login.

Requirements:

- Passwords must never be stored in plain text.
- Use secure sessions or signed authentication tokens.
- Protect all server routes.
- Validate user permissions on the server, not only in the interface.
- Rate-limit login attempts.
- Validate all submitted data.
- Restrict uploaded file types.
- Restrict maximum upload size.
- Generate non-guessable file names.
- Do not expose storage credentials to the browser.
- Include CSRF protection where required by the chosen architecture.
- Use secure cookies in production.
- Log security-sensitive administrative actions.

Create a seeded administrator account for development only.

The initial password must come from an environment variable and must not be committed to source control.

25. Validation rules

Require:

- Observation title.
- Category.
- Priority.
- Observation date.
- Reporting user.

Require valid coordinates when GPS location is supplied.

Do not require coordinates if the user deliberately chooses to continue without GPS.

Require:

- Action title.
- Priority.
- Status.

Require a completion note when an action is marked completed.

Require a cancellation reason when an observation or action is cancelled.

Ensure due dates and observation dates use the user's local timezone.

Use the Europe/London timezone as the default.

---

- User does not have permission.

29. MVP acceptance criteria

The first useful release will be accepted when all of the following are true:

1. A user can log in securely.
2. A team member can create an observation from a mobile phone.
3. The app can capture or manually set the observation location.
4. A user can upload at least one photograph.
5. A manager can view the observation.
6. A manager can create and assign an action.
7. The assigned team member can see the action in My Actions.
8. The team member can mark the action completed and add a completion note.
9. The manager can see the completed action and activity history.
10. Observations can be viewed on a map.
11. Records can be filtered by category, priority, status and location.
12. The app works at common mobile screen sizes.
13. A field observation can be saved when connectivity is lost and synced later.
14. The app does not lose an unsynced record.
15. A manager can produce a basic monthly summary.

30. Important implementation instructions

Before writing large amounts of code:

1. Create a concise architecture summary.
2. Create the proposed database schema.
3. List the packages and external services required.
4. Identify any implementation risks.
5. Generate the initial project structure.
6. Implement Phase 1 first.
7. Run migrations and seed the database.
8. Test the complete observation-to-action workflow.
9. Fix errors before moving to Phase 2.
10. Keep the README updated as the application develops.

Do not replace working functionality merely to change frameworks or libraries.

Prefer straightforward, maintainable code over unnecessary abstraction.

Add comments only where the reasoning is not obvious.

Use reusable components for forms, status labels, priority labels, image upload and map filters.
